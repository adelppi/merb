- 日付: 2026-11-03
- 決めた人: adelppi
- 関係する Issue と PR: #13
- 解決した未解決の項目: OQ-007
- 置き換える記録: なし

## 背景

出題の画面を作り始める前に、ソースコードの構成と、使う設計パターンを決める必要があった。`vision.md` の判断の基準にある「出す問題の読み方が正しいこと」を守るため、判定の処理を単体テストで確かめやすい形にしたい。

前提にした条件は次のとおり。

- DB、認証、サーバーでの処理を持たない。問題はリポジトリの JSON で、ページはビルドのときに静的に作る（[D-0003](D-0003-tech-stack.md)）。
- 学習の記録を保存しない（`vision.md` の「やらないこと」）。状態は出題の画面の中だけで持てばよい。
- 判定と札の生成は、すでに `src/questions/` に純粋な関数として書いてあり、Vitest で確かめている。
- 画面は、分類を選ぶ画面と出題の画面のほぼ2つになる見込み。

## 決定

### 採る案

| 候補 | 使い方 |
|---|---|
| Functional Core, Imperative Shell | 判定、札の生成、出題の進行を純粋な関数に書き、React のコンポーネントは表示と入力だけを受け持つ。いまの `src/questions/` の形をそのまま広げる |
| 状態機械（`useReducer`） | 出題の進行を「解いている」「正解」「不正解」「答えを見ている」の状態と、その移り方として reducer に書く。reducer は純粋な関数なので Vitest で確かめられる |
| カスタムフック | reducer と、札を混ぜる処理を `useQuiz` のようなフックにまとめ、コンポーネントはその戻り値を表示する |
| 外から来たデータを境目で Zod にかける形 | 問題の JSON を読むところで Zod にかけ、以降は型の付いた値として扱う。ビルドのときに読むので、利用中の負担はない |
| 機能ごとにフォルダを分ける構成（軽く） | 下の「ディレクトリの構成」のとおり、問題、出題の進行、表示の部品で分ける |

### 一部だけ採る案

| 候補 | 理由 |
|---|---|
| container / presentational | 状態はカスタムフックに持たせるので、container のコンポーネントは作らない。札や数式の表示の部品は、props だけで描く presentational にする |
| DI | 仕組みとしては入れない。乱数だけは、札を混ぜる関数の引数で渡し、テストでは固定した値を渡す |
| repository | 問題を読む関数を1つ置けば足りる。クラスや interface は作らない |

### 採らない案

| 候補 | 理由 |
|---|---|
| クリーンアーキテクチャ、オニオンアーキテクチャ、port & adapter（ヘキサゴナルアーキテクチャ） | 隔てる外部（DB、外部の API）がない。層を分けても、コードを置く場所が増えるだけになる |
| レイヤードアーキテクチャ | 同じ理由。採る案の「処理と表示を分ける」で足りる |
| DDD の戦術的な設計（エンティティ、値オブジェクト、集約） | 問題、札、回答のほかに扱うものが少なく、集約やエンティティを立てる対象がない |
| 値オブジェクト、ブランド型 | Zod から作った型で足りる。取り違えやすい値が出てきたら考え直す |
| MVC | React と App Router の作りに合わない |
| MVVM | カスタムフックが ViewModel の役をするので、名前を付けて分けなくてよい |
| Flux（Redux、Zustand） | 状態は出題の画面の中で閉じる。`useReducer` で足り、依存を増やさない |
| 状態機械を XState で書く形 | 状態は4つほどで、`useReducer` で書ける。依存を増やさない |
| Context | 状態を使うのは出題の画面の中だけなので、props で渡せる。深く渡す必要が出たら考え直す |
| Compound Components | 部品を組み合わせて使う場面がない |
| Feature-Sliced Design | 決まりが多く、画面が2つほどのアプリには重い |
| Atomic Design | 部品が少なく、どの段階に入れるかを決める手間のほうが大きい |
| Strategy | 判定の決まりは1つだけ（[D-0004](D-0004-question-format.md)） |
| Result 型 | 誤りを返す処理は問題の JSON の検査だけで、いまの文言の配列で足りる |
| CQRS、イベントソーシング | 保存するデータがない |
| BFF、API Route、Server Actions | サーバーで処理することがない（[D-0003](D-0003-tech-stack.md)） |

### 処理と UI のコードの分け方

判定や札の生成などの処理は、UI のコードと分ける。処理は `src/questions/` と `src/quiz/` に純粋な関数として置き、UI のコードは `src/components/` と `src/app/` に置く。

### 出題の状態の持ち方

出題の状態（札の位置、正誤、次の問題）は、出題の画面の中で `useReducer` で持つ。reducer と、それをまとめる `useQuiz` は `src/quiz/` に置く。

### Server Component と Client Component の境目

- ページ（`page.tsx`）は Server Component にし、ビルドのときに問題の JSON を読んで Zod にかける。
- 出題の画面は、札のドラッグがあるので Client Component にする。ページから、選んだ分類の問題を props で渡す。
- 数式の表示は、KaTeX で描いた結果を表示するだけなので、Client Component の中で使えるように props だけで描く部品にする。

### 札を混ぜるときの乱数の固定

札を混ぜる関数は、乱数を返す関数を引数で受け取る。テストでは、決まった値を返す関数を渡して結果を固定する。

### ディレクトリの構成

```
src/
  app/[locale]/       ページ。薄く保ち、問題を読んで画面の部品に渡すだけにする
  questions/          問題の形、札の生成、判定、問題の JSON の検査（いまのまま）
  quiz/               出題の進行。reducer、札を混ぜる処理、次の問題を選ぶ処理、useQuiz
  components/         表示の部品。数式、札、回答エリアなど
  i18n/               next-intl の設定
content/              観点シートと問題の JSON（いまのまま）
```

- 出題の画面の部品も、`src/quiz/` ではなく `src/components/` に置く。`src/quiz/` には出題の進行の処理とフックだけを置く。
- テストは、いまの決まりのとおり、テストするファイルと同じフォルダに置く。
- `src/questions/check.ts` は単体テストからしか使わないが、問題の形の決まりと近いので `src/questions/` に残す。
- `src/app/[locale]/` と `src/i18n/` は、next-intl を入れるときに作る。

## ほかの選択肢

- 採らない案は、上の「採らない案」の表のとおり。
- 出題の画面の部品を `src/quiz/` にまとめ、`src/components/` には複数の画面で使う部品だけを置く案。処理と表示の置き場を分けるほうを選んだ。

## 根拠

- 判定、札の生成、出題の進行を純粋な関数にすると、React を動かさずに Vitest で確かめられる。`vision.md` の判断の基準の1つ目「出す問題の読み方が正しいこと」に合う。
- 隔てる外部も保存するデータもないので、層を分ける構成や状態の置き場を1つにする仕組みは、置き場と依存を増やすだけになる。
