## 背景

問題は LLM で作り、確かめてからリポジトリの JSON として持つ（[D-0002](D-0002-question-source.md)）。出題の機能を作る前に、正解、まぎらわしい札、分類との対応、判定のしかたと、ファイルの置き場を決める必要があった。

## 決定

- 正解は、札の文字列の配列で持つ。読み方が複数ある数式では、正解を複数持つ。まぎらわしい札は、正解とは別の配列で持つ。
- 出す札は、どの正解も組み立てられるだけの正解の札と、まぎらわしい札を合わせたものにする。ある正解で使わない札は、そのとき余る。
- 札には句読点を入れない。判定では、札の文字列をそのまま比べ、大文字と小文字を区別する。答えを見せるときのカンマ付きの読み方は、札とは別に持てるようにする。
- 出題の範囲で選ぶ分類は、観点シートの節の8つにする。各問題には、もとにした観点の行も書く。
- 観点シート、問題を作るプロンプト、問題の JSON は、`content/` にまとめて置く。

詳しい形は [問題の JSON の形](../specs/question-format.md) に書いた。

## ほかの選択肢

- 札を id 付きの一覧にし、正解を id の並びで持つ案。手で書く量が増えるので採らなかった。
- 判定で大文字と小文字を区別しない案。観点シートには `F of omega` と `f of t` のように、大文字と小文字で別のものを指す式がある。区別しないと、`F` と `f` の札を入れ替えても正解になるので採らなかった。
- カンマも札にして、置く場所まで判定する案。採らなかった。
- 分類を節だけにして、観点の行を持たない案。採らなかった。
- 節 8 を小節で分け、分類を10にする案。採らなかった。
- 観点シートとプロンプトを `docs/` に、問題の JSON を `content/` に分けて置く案。採らなかった。

## 根拠

- [D-0003](D-0003-tech-stack.md) では、正解の読み方をその問題の札で組み立てられるかを検査すると決めた。この形では出す札を正解から作るので、その条件はいつでも満たされる。そこで、答えを見せるときの読み方が札と食い違っていないかを、検査の条件に入れた。

## 影響

- `docs/specs/question-format.md` を書いた。
- 観点シートを `content/perspectives.md` に入れた。
- 問題を作るプロンプトを `content/prompt.md` に入れた。
